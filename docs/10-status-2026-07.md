## ЧП 2026-07-27: отказала СЕТЬ между малинкой и роутером (вскрытие 2026-07-28)

Вскрытие проведено вживую (ssh на 192.168.88.2 и на роутер). Что показали
улики — важнее того, что казалось:

- **Малинка была ЖИВА весь час.** Панель и бот непрерывно писали в журнал
  20:57–21:56. Пинг проходил, процессы работали.
- **Умер именно DNS.** Бот не мог резолвить `api.telegram.org`, деплой —
  `github.com` («Temporary failure in name resolution»). Резолвер самой
  малинки — она сама (`/etc/resolv.conf` → 192.168.88.2), так что дом и
  малинка ослепли одновременно.
- **Легла связь малинки с роутером, а не AdGuard.** Решающая улика — журнал
  событий панели: «RouterOS 192.168.88.1:8728 недоступен» в 19:54, 20:25,
  20:55, 21:26 (реже не пишется — троттлинг 30 мин), то есть API роутера
  был недоступен НЕПРЕРЫВНО минимум с 19:54 до 21:26. AdGuard за это время
  не падал (`Restart=always` не сработал ни разу) и не оставил записей: он
  просто не мог достучаться до upstream.
- **Что именно легло — сетевой стек малинки или сам роутер — не отличить.**
  У Pi 3 сеть висит на USB (`smsc95xx`) и это известное слабое место, но
  kernel-журнал прошлой загрузки утерян целиком. Обе версии одинаково
  объясняют всё: и слепой DNS, и недоступный API, и «малинка не отвечает».
- **Версий «OOM», «SD», «питание» не подтвердилось:** следов OOM-killer в
  журнале прошлой загрузки — 0; `vcgencmd get_throttled` = `0x20000`
  (под-вольтажа не было, только ограничение частоты); ошибок mmc/ext4 нет;
  диск занят на 73%, не переполнен.
- **Почему причина всё же утеряна:** журнала до 27 июля 20:57 не существует
  вовсе, и рядом лежит битый файл `user-1000@…journal~` от 21:56 — жёсткое
  обесточивание съело недописанные журналы. То, что случилось с AdGuard
  ДО этого часа, не восстановить.

**Выводы, уже воплощённые в коде:**

1. Пинговая проба бесполезна для этой аварии — сторож на роутере
   (`mikrotik/pi-guard.rsc`) теперь РЕЗОЛВИТ имя через малинку
   (`:resolve … server=`, синтаксис проверен на живом RouterOS 7.23.2).
2. Добавлен сторож на самой малинке: `deploy/dns-selfheal.sh` +
   `homesec-dnscheck.timer` — раз в минуту резолвит имя и перезапускает
   AdGuard, если тот перестал отвечать (антидребезг 10 минут). Но сначала
   пингует роутер: если сети нет, AdGuard не виноват — тогда только громкая
   запись в журнал, без бесполезного перезапуска (сценарий этого ЧП).
3. Меры про watchdog/журналы/zram остаются как страховка, но причина не в
   памяти — приоритет у них ниже.
4. Замеры памяти на проде: панель ~65 МБ, бот ~141 МБ, AdGuard ~126 МБ
   (из 906 МБ). Потолки в юнитах выставлены от этих чисел.

Свежий срез всегда можно снять одной командой:

```bash
sudo bash /opt/homesec/deploy/pi-hardening.sh --diagnose
```

**Шаг 2 — меры (владелец одобрил «watchdog вместо ежедневного ребута»;
cron-reboot отвергнут как костыль, маскирующий причину). Реализованы в
ветке `audit/2026-07`, применяются двумя ручными действиями:**

```bash
sudo bash /opt/homesec/deploy/pi-hardening.sh   # watchdog + журналы + zram + retention AdGuard
```

- watchdog (`RuntimeWatchdogSec=15`), потолок journald (64 МБ), zram-swap,
  обрезка журнала AdGuard (24 ч) и статистики (7 дней) — всё в этом скрипте,
  он идемпотентный; если `/dev/watchdog` нет, добавит `dtparam=watchdog=on`
  и попросит перезагрузку;
- `MemoryHigh/MemoryMax` для homesec и homesec-bot приезжают обычным
  деплоем (update.sh теперь переустанавливает юниты при изменении).

На роутере (залить `mikrotik/pi-guard.rsc` в Files, вписать токен бота и
chat_id, затем `/import file-name=pi-guard.rsc`) — сторож малинки: раз в
минуту РЕЗОЛВИТ имя через малинку, три неудачи подряд → роутер сам берёт DNS
на себя и шлёт алерт в Telegram, DNS вернулся → контроль возвращается сам.
DHCP не трогает: вместо этого включает заранее заведённые ВЫКЛЮЧЕННЫЕ правила
«спасательного круга» (заворот DNS-запросов к 88.2 на роутер + hairpin по
правилу №3), поэтому лечится мгновенно и для всех, включая гостей.
**Проверить вживую обязательно** — воспроизвести ровно ту аварию:
`sudo systemctl stop AdGuardHome` на малинке, через 3 минуты глянуть
`/log print where message~"hs:"`, потом `start`. Правила заворота на живом
роутере не проверялись (проверены только селекторы и синтаксис пробы).

Аварийный откат руками (тоже новое, залить `emergency-dns-rollback.rsc`):
`/import file-name=emergency-dns-rollback.rsc` — см. docs/05-operations.md.

## Аудит и правки 2026-07-15 (все в проде, main)

- **DHCP-DNS фикс**: LAN-сеть роутера раздавала DNS 88.1 вместо 88.2 →
  AdGuard видел только роутер как клиента, персональные политики (safe
  search детям и т.п.) не работали. Исправлено (`/ip dhcp-server network`
  через `[find comment=defconf]`; селектор `find address=` НЕ матчит
  IP-префикс на 7.23!). Теперь AdGuard видит реальные IP устройств.
- **Анти-обход восстановлен**: DoH-блок был на все порты (ломал upstream) →
  заменён на drop tcp+udp/443 к hs-doh для hs-managed; DoT(853) включён.
  QUIC-для-детей осознанно ВЫКЛЮЧЕН (не рвать стриминг на TV).
- **Роутер**: отключены telnet/ftp/api-ssl/reverse-proxy (открыты только
  ssh/www/winbox с LAN и api для Pi).
- **Контроль детей**: глобальный NSFW-блоклист HaGeZi в AdGuard (панель его
  не трогает); включена квота игр детям 120 мин/день.
- **Хардненинг ядра** (commit harden…): `get_self_ips` fail-safe —
  статический якорь `HS_SELF_IPS` (по умолч. 192.168.88.2) + fail-closed в
  reconcile (пустой self_ip → роутер не трогаем); межпроцессный flock вокруг
  reconcile (панель и бот — разные процессы); IntegrityError в
  discover_devices; троттлинг журнала ошибок (30 мин).
- **Бот**: опц. `HS_TELEGRAM_USER_IDS` — доп. проверка from_user.id (защита
  групповых чатов). Пусто = прежнее поведение.
- **Панель**: дашборд → родительская консоль (карточки по людям, полосы
  экранного времени, онлайн, пауза); быстрые действия в один тап (пауза
  30м/1ч/до утра, +30 мин бонус, групповая пауза/«Ужин»); security-заголовки
  (CSP, X-Frame-Options), rate-limit логина (8 попыток/15 мин → 429).

## Киллер-фича «попросить ещё времени» (2026-07-16, в проде, main)

- Реализована (аналог Family Link под сетевой контроль без агента на
  устройстве). Ключевой разворот: страница-перехват на HTTP ребёнку почти
  не видна в мире HTTPS, поэтому канал к нему — САМА панель на LAN
  (`/me`, публичная): открывает наш хост напрямую → нет проблемы
  сертификата, и она доступна даже при полной блокировке (hs-blocked →
  панель:8000 разрешён). Captive-portal для полностью заблокированных уже
  заворачивал OS-пробы на панель существующими правилами — firewall НЕ
  трогали.
- Компоненты: модель `BonusRequest` + миграция №3; `services/bonus.py`
  (антиспам 1/10мин, TTL 24ч); страница `/me` (полосы квот, кнопка
  «Попросить ещё времени», автообновление 20с); та же кнопка на `/blocked`;
  событие `bonus_request` → бот шлёт родителю `[+15][+30][до конца дня]
  [Отказать]` → `add_bonus_time`+reconcile, заявка помечается (идемпотентно).
- DNS-имя для закладки: `vremya.dom → 192.168.88.2` (AdGuard rewrite,
  выбрано владельцем). Закладка детям: `http://vremya.dom:8000/me`.
- Round-trip проверен на проде вживую (req#1: заявка → пуш → «Отказать» →
  denied за 346 мс, бонус не создан).
- **Эмпирика iOS (проверено на iPhone владельца, 2026-07-16)**: перехват
  работает — ввод любого `http://` адреса показывает заглушку мгновенно; но
  системное окно captive-portal при переподключении к ЗНАКОМОЙ сети iOS НЕ
  показывает (просто значок «нет интернета» в настройках Wi-Fi) — всплывает
  надёжно только для новых/забытых сетей. Вывод: главный вход для детей —
  иконка «Время» на домашнем экране; captive-portal — бонус для гостей.
  Это потолок технологии (Family Link решает агентом в ОС), не дефект.
