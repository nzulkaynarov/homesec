### [баг] merge_devices теряет дневной учёт минут, бонусы и заявки дубля ✅
`backend/app/ai/tools.py:575`

При объединении устройств (сценарий ротации «приватного» MAC, ради которого фича и сделана) merge_devices переносит только DeviceMac и ip, после чего db.delete(dup) (строка 575). Ротация приватного MAC у iOS/Android — регулярное событие в этой сети (см. инцидент дублей IP в CLAUDE.md), то есть потеря минут — не экзотика, а повторяющийся путь.

**Фикс:** В merge_devices перед db.delete(dup) перевесить связанные записи на target: UPDATE QuotaUsage/BonusRequest SET device_id=target.id и QuotaBonus SET target=str(target.id) WHERE target_type='device' AND target=str(dup.id); для QuotaUsage за сегодняшнюю дату при совпадении (date, category) суммировать minutes в одну строку (или оставить две — _usage_map на quota.py:181 корректно суммирует дубли). ### [баг] Удаление устройства оставляет orphan-строки device_macs → неперехваченный IntegrityError валит reconcile-тик ✅
`backend/app/routers/devices.py:152`

delete_device делает db.delete(dev) без чистки связанных таблиц, а FK в SQLite не включены (нет PRAGMA foreign_keys в backend/app/db.py:17-25), поэтому строки device_macs с device_id удалённого устройства остаются (у Device нет ORM-relationship к DeviceMac — каскада нет). Когда MAC удалённого устройства (его основной или любой ранее «объединённый» приватный MAC) снова появляется в DHCP-lease, discover_devices не находит его в known (orphan отфильтрован проверкой `if dev is not None` на enforcement.py:167) и идёт по ветке создания: первый commit (новый Device) проходит — devices.mac освободился при удалении, — а второй commit `db.add(DeviceMac(device_id=dev.id, mac=mac)); db.commit()` (enforcement.py:192-193) падает IntegrityError по UNIQUE device_macs.mac (models.py:66), потому что orphan-строка всё ещё держит этот MAC. Этот commit НЕ обёрнут в try/except (защищён только первый, строки 179-191). IntegrityError пролетает через reconcile (там ловятся только MikrotikError/AdGuardError) до scheduler._tick — весь тик enforcement пропущен ДО address_list_sync: блокировки/квоты в эту минуту не применяются. Вдобавок у пересозданного устройства строка в device_macs так и не появляется никогда (на следующем тике оно матчится по основному MAC), т.е. рассинхрон в базе постоянный, и каждая новая ротация приватного MAC на «осиротевший» адрес стоит ещё одного сорванного тика.

**Фикс:** Двухслойно: (1) в delete_device перед db.delete(dev) явно удалять связанные строки: DeviceMac, а заодно BonusRequest/QuotaUsage/RegistrationRequest по device_id (у них FK нет вовсе — просто int); (2) обернуть второй commit в enforcement.py:192-193 тем же паттерном, что и первый: except IntegrityError → rollback → найти существующую строку device_macs по mac и перепривязать её к dev.id (или удалить orphan и повторить вставку), чтобы ядро самовосстанавливалось на грязной базе.

### [безопасность] Идентификация устройства на /me, /me/ask, /blocked — по подменяемому IP клиента ✅
`backend/app/routers/portal.py:70`

Все публичные страницы определяют устройство запросом select(Device).where(Device.ip == ip), где ip = request.client.host (portal.py:23-24, 30, 49, 70). IP в LAN подменяем без каких-либо инструментов: ребёнок вручную ставит статический IP чужого устройства (выключенного телевизора, устройства взрослого) в настройках Wi-Fi. Последствия: (а) чтение чужих данных — имя устройства, остаток квот, статус ограничения и последней заявки владельца этого IP; (б) отправка bonus-заявки от имени чужого устройства — родитель одобряет «телевизору», а временем пользуется ребёнок, сидящий на его IP; (в) главное — вся сетевая политика (hs-blocked/hs-managed на роутере) тоже ключуется по IP, поэтому взяв IP взрослого устройства, ребёнок наследует и его отсутствие ограничений, а его старый IP остаётся в hs-blocked впустую. Middleware auth.py:71 через restriction_for_ip разводит по тому же IP — заблокированный, сменив IP, перестаёт считаться заблокированным. Это потолок безагентной технологии, но сейчас он ничем не подпёрт на уровне L2.

**Фикс:** Закрыть на уровне роутера: в DHCP-сервере MikroTik включить add-arp=yes и на bridge поставить arp=reply-only — тогда самовольные статические IP (без выданного lease) вообще не получают связности, и IP снова становится достоверным идентификатором. Дополнительно в /me/ask панель может сверять MAC: запросить ARP-запись роутера для client IP (mikrotik.py уже умеет ходить в API) и сравнить с dev.mac, при расхождении — отклонять заявку и логировать событие.

### [продукт] Ротация приватного MAC мгновенно снимает блокировку и обнуляет квоты ребёнка ✅
`backend/app/services/enforcement.py:260`

Блокировки (blocked_manual, паузы, расписания) и счётчики квот привязаны к строке Device, а желаемое состояние — к dev.ip. **Фикс:** Карантин для новых устройств со случайным MAC: считать их заблокированными (или наследовать ограничения устройства с совпадающим hostname) до явного решения родителя; как минимум — включить block_unknown в проде и/или при device_maybe_same автоматически применять к новичку ограничения «близнеца» до merge.

### [безопасность] Mangle-метка hs-dns без ограничения интерфейса открывает AdGuard как резолвер для WAN-сегмента
`mikrotik/homesec-base.rsc:50`

Правила «hs: DNS mark udp/tcp» (строки 50-51) вешают метку hs-dns на ЛЮБОЙ входящий пакет с dst-port 53 и dst != 192.168.88.2 — без src-address или in-interface-list, то есть и на пакеты, пришедшие с ether1 (WAN). Устройство из сегмента Huawei (192.168.0.0/24) шлёт DNS-запрос на WAN-адрес MikroTik (192.168.0.161:53): пакет метится, dst-nat заворачивает его на малинку, а defconf-правило forward «drop all from WAN not DSTNATed» пропускает dst-натированный трафик — защита input-цепочки обходится. Итог: AdGuard становится резолвером для всего сегмента за Huawei, его лог замусоривается чужими запросами с IP роутера (после hairpin masquerade). От интернета прикрывает только двойной NAT: проброс порта 53 на Huawei превратил бы это в открытый резолвер (усилитель DNS-амплификации).

**Фикс:** Добавить в оба mangle-правила `in-interface-list=!WAN` (не `=LAN`: bridge-guest не входит в список LAN, и заворот гостевого DNS сломался бы). На живом роутере — `set` существующих правил по comment, в base.rsc — поправить строки для будущих развёртываний.
